## ジェネリック関数の本体に何を書けるか

TypeScriptで `function f<T>(x: T): T` と宣言し、その本体を書くとしよう。
この `T` は型パラメータと呼ばれる型の変数で、どの型になるかは呼び出す側が呼び出しのたびに決めるため、本体を書く時点では中身が決まっていない。
実際に書いてみると、受け取った `x` をそのまま返す以外に、本体に書けることはほとんどない。

試しに本体を `return 1;` とだけ書くと、TypeScript 7.0.2 は `error TS2322: Type 'number' is not assignable to type 'T'.` という型エラーを出す（`number` 型の値は `T` 型に代入できない、という意味である）。
このエラーには `'T' could be instantiated with an arbitrary type which could be unrelated to 'number'.` という補足の行が続き、`T` は呼び出しのたびに `number` と無関係な型にもなりうる、と拒んだ理由を添えている。
`1` が拒まれるのは `1` という値を選んだからではなく、本体の中で新しく作ったどの値も、`T` がどの型になっても属する値だとは言えないからである。

型を `number` に固定した `function g(x: number): number` であれば、`return 1;` も `return x + 1;` も型検査を通り、本体の書き方はいくらでもある。
シグネチャ（関数の引数と戻り値の型の宣言）で `T` の中身を何も指定していない `f` のほうが、書ける本体はかえって少なく、しかもそのシグネチャのどこにも「`x` を返せ」とは書かれていない。
型はこの関数について何を知らず、知らないことによって何を決めているのかが、この序章の問いである。

## 比喩は何を保ち、何を捨てるのか

本書でいう比喩とは、ある対象を別の対象に対応づける写像のうち、元の対象の構造の一部を保ち、残りを捨てるもののことである（写像とは、一方の各要素に他方の要素を一つ対応させる規則のことで、配列の `map` に渡す関数もその一つである）。
たとえば地下鉄の路線図は、駅の並び順と路線どうしの乗り換えを保ったまま街を紙の上に写し、駅のあいだの実際の距離や線路の曲がり具合を捨てている。
だから路線図で乗り換えの道順は正しく調べられるが、定規を当てても実際の距離は測れず、比喩から引き出してよい結論は保たれた構造についてのものに限られる。

構造の一部を捨てることは、比喩の欠点ではなく、比喩を使う理由である。
もし駅のあいだの距離や線路の曲がり具合まですべて写していたら、路線図は縮尺どおりの街の地図と変わらなくなり、乗り換えの道順を一目で追うという用途には使いにくくなっただろう。
違う二つのものを同じものとして扱えるのは、その違いを捨てたからであり、何を捨ててよいかは、写した先で何を調べたいかによって決まる。

個々のものの違いを捨てて共通する形だけを残すことを抽象化といい、大きさも毛色も違う犬たちを「犬」という一語でまとめて呼べるのは、一匹ごとの違いを捨てているからである。
アルゼンチンの作家ボルヘスの短編「記憶の人フネス」は、この違いを捨てられない人物を描いており、主人公の青年フネスは落馬をきっかけに、見たものや聞いたものを細部まで覚えていて何一つ忘れられなくなる。
フネスには、「犬」という一語が大きさも形も違う多くの犬をまとめて指すことが理解しにくく、3時14分に横から見た犬と3時15分に正面から見た犬が同じ名で呼ばれることさえ不快だった。
物語の語り手は、そのフネスがあまり考えることのできない人だったのではないかと疑い、続けて、考えるとは違いを忘れ、一般化し、抽象化することだと述べる。
抽象化は、一つとして同じもののない出来事の連なりを、限られた数の言葉と限られた記憶で扱えるのはなぜか、という問いに答える考え方であり、フネスの話は、違いを一つも捨てられなければ、ものを一般的な言葉でまとめて扱うことさえ難しくなることを示している。

型もまた、個々の値の違いを捨てて、それがどの種類の値かだけを残す点で抽象化に似ており、`number` 型の変数について型検査が見るのは、中身が `1` か `42` かではなく、数であるかどうかだけである。
ただし、型と抽象化のこの対応は「似ている」と言えるだけの類推であり、型が値の違いを捨てることからどんな結論が導けるのかは、まだ何も示していない。

## 中身を知らない関数を型で書く

冒頭の `f` の本体に `return x;` の一行だけを書いたのが次の関数 `id` で、TypeScript 7.0.2 はこれを型エラーなしで通す。

```ts
function id<T>(x: T): T {
  return x;
}

export const n: number = id(1);
```

本体は `T` について何も知らないまま書かれているが、呼び出す側が `1` を渡せば戻り値は数として扱え、最後の行のように `number` 型の変数に代入しても型検査を通る。

同じ関数を、本書でTypeScriptと並べて使う関数型言語のHaskellで書くと次のようになり、GHC 9.6.7 はこれも言語拡張なしで型エラーなしに通す。

```haskell
identity :: a -> a
identity x = x
```

1行目の `identity :: a -> a` は「どんな型 `a` についても、`a` 型の値を受け取って `a` 型の値を返す」と読む型の宣言で、2行目の `identity x = x` は、受け取った `x` をそのまま返す本体である。
Haskellでは型の宣言に小文字で始まる名前を書くだけで、それが TypeScript の `T` と同じく呼び出しのたびに決まる型の変数として扱われるので、`<T>` にあたる宣言は書かない。

中身を見ないことで式の形を縛るしくみはプログラムの外にもあり、物理学の次元解析は、量の数値を見ずに単位だけを手がかりに、ある量を表す式の形を絞り込む方法である（以下では、単位を型に、数値を値に見立てて読む）。
例として、振り子が一往復するのにかかる時間（周期）を、糸の長さ L（単位はメートル、m）、重力加速度 g（地上で落ちる物の速さが1秒あたりに増える量で、単位は m/s²）、おもりの質量 M（単位はキログラム、kg）から求める式を考えよう。
次元解析では、量を掛けたり割ったりすると単位も同じ掛け算や割り算で組み合わさり、等号の両辺で単位が一致しない式は、数値を入れて確かめる前に誤りとして退けられる（この点で、実行する前に型の合わない式を退ける型検査に似ている）。

## 型だけから導けること

冒頭では `f` の本体に `x` を返す以外ほとんど何も書けないと述べたが、関数が必ず値を返して終わり（例外を投げたり無限ループに入ったりしない）、関数の外の状態を読み書きせず、引数の中身を調べて場合分けしない、という三つの前提を置けば、「ほとんど」を外した主張を型だけから導ける。
この前提のもとでは、本体は `T` がどの型かを知らないので `T` 型の値を新しく作れず、手元にある `T` 型の値は引数の `x` だけだから、戻り値は `x` のほかにありえない。
したがって、前提を満たす `<T>(x: T) => T` 型の関数はどれも、受け取った値をそのまま返す恒等関数であり、このように型だけから関数のふるまいについて導かれる定理は自由定理と呼ばれ、その一般的な導き方は Philip Wadler の1989年の論文「Theorems for free!」に示されている。

前提を外すとこの結論は成り立つとは限らず、たとえば本体で必ず例外を投げる関数も `<T>(x: T): T` と宣言すれば型検査を通るが、値を一度も返さないので恒等関数ではない。
しかも TypeScript 7.0.2 の型検査は三つの前提を確かめておらず、本体で例外を投げても、無限ループに入っても、関数の外の変数を書き換えても、`typeof` で引数の中身を調べても、`<T>(x: T): T` と宣言した関数は型エラーなしに通る。
したがって TypeScript で書いた関数について自由定理が言えるのは、書き手が三つの前提を自分で守っている場合に限られ、引数の中身を調べないという前提が崩れたときに何が起こるかは4章で扱う。

次元解析でも前提を一つ明示すれば同じように導出でき、周期が、L、g、M をそれぞれ何乗かして掛け合わせた L<sup>a</sup>g<sup>b</sup>M<sup>c</sup> に、単位を持たない数を係数として掛けた形で書けると仮定すると、右辺の単位は m<sup>a</sup>(m/s²)<sup>b</sup>kg<sup>c</sup>、つまり m<sup>a+b</sup>s<sup>−2b</sup>kg<sup>c</sup> になる。
左辺の周期の単位は秒（s）だけなので、両辺の単位が一致するには kg の指数 c が 0、s の指数 −2b が 1、m の指数 a+b が 0 でなければならず、そこから b = −1/2、a = 1/2 が決まるので、周期は √(L/g) に比例し、質量 M は式に入りえないことが、数値を一つも見ずに導かれる。
ただし単位から決まるのは比例の形までであり、振れ幅が小さいときの周期の式 2π√(L/g) にある係数 2π は単位を持たない数なので、次元解析からは出てこない。

二つの導出はどちらも、中身を見ないという制約からありうる答えの範囲を狭めており、三つの前提を満たす `<T>(x: T) => T` 型の関数は恒等関数ただ一つに、振り子の周期の式は √(L/g) に単位を持たない数を掛けた形に絞られた。
ただし、型が狭めた範囲がいつも一つの答えになるとは限らず、振り子の式で係数が単位から決まらずに残ったように、型から導いてよい結論は、狭められた範囲に残るどの候補についても成り立つことに限られる。
本書では、この二つのように前提から一歩ずつ追える結論を導出と呼び、型と抽象化の対応のように似ていると言えるだけのものを類推と呼んで、前者は「〜だから〜である」、後者は「〜に似ている」と書き分ける。

## 型という写像が捨てたもの

次元解析で係数 2π が出てこなかったのは、量を単位に写すときに数値が捨てられ、2π も 1 も 3 も単位を持たない数として同じ「単位なし」に写されて、単位だけを見る側からは区別できなくなるからである。
同じように、関数を `<T>(x: T) => T` という型に写すと、本体の中で何が起きるか（例外を投げるか、止まらなくなるか、外の状態を読み書きするか、引数の中身を調べるか）が捨てられ、前の節で三つの前提を型の外から置かなければならなかったのはそのためである。
型から導いた結論は写像が保った構造についてのものに限られるので、捨てられたほうを知るには、振り子なら運動の方程式を解くか周期を測り、関数なら本体を読むか動かしてみるというように、型の外で確かめる必要がある。

## 各章の五つの段階と二つの言語

以降の各章もこの序章と同じ五つの段階を同じ順で踏み、TypeScriptを書く人が出会う場面から入り（入口）、そこにつながる哲学の考えを平易に要約し（思想の要約）、その考えをコードに書いて型検査にかけ（型で書く）、型で書いたからこそ言える結論を導き（降ってくる帰結）、最後にその対応づけが何を捨て、どこで成り立たなくなるかを確かめる（写像が忘れたもの）。
コードは読者が毎日書くTypeScriptを主に使い、TypeScriptでは素直に書けない構造が要る場面や、型から導いた結論を言語どうしで比べたい場面ではHaskellでも書いて、同じ考えを二つの言語で書いたときにどこで結論が分かれるかも議論の材料にする。
値の違いを捨てる型そのものも、TypeScriptではJavaScriptに変換されるときに型の注釈ごと取り除かれて実行中のプログラムには残らず、そのとき型はプログラムのどこにあるのかが1章の問いになる。
